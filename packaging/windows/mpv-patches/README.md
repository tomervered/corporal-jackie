# Patches to mpv for the Windows build

`build-mpv.sh` applies every `.patch` here, in name order, to the mpv source before building it. The patched files keep mpv's licence (LGPL-2.1-or-later for these).

- `0001-d3d11-dxinterop.patch` adds a hardware-decoding bridge, `d3d11-dxinterop`, that puts Direct3D 11 frames on a normal (WGL) OpenGL context through `WGL_NV_DX_interop2`. NVIDIA, AMD and Intel drivers support that extension. mpv already has such a bridge for Direct3D 9, but not for Direct3D 11. Without it, mpv has no Direct3D 11 device when the app draws through mpv's OpenGL render API, and `vf=d3d11vpp` (which runs NVIDIA RTX and Intel Video Super Resolution) cannot load. Each frame is converted to one 8-bit RGB texture by the Direct3D 11 video processor, because the interop cannot share NV12 or P010 textures. The Direct3D 11 device is made on the graphics card the OpenGL context runs on (matched by vendor), because on a laptop with two cards the default one is often the other card, and the interop only works on one card.
- `0002-intel-vsr-copyback.patch` adds the filter option `intel-copyback` to mpv's `d3d11vpp`: for Intel VSR on the `d3d11-dxinterop` bridge, each upscaled frame is copied back to system memory (`mp_image_hw_download`) instead of reaching the shared texture. See "Intel VSR compatibility mode" below.

The app only uses this bridge while NVIDIA or Intel VSR is picked in Settings. Otherwise it asks mpv for copy-back decoding (`hwdec=auto-copy-safe`), the same path as before the patch.

**Waiting for OpenGL.** Direct3D must not write the next frame into a texture OpenGL is still reading, or the picture tears. NVIDIA's driver needs OpenGL's work finished before the texture is unlocked (`finish`), a stall that shows as stutter on Intel. Every other card gets `ring`: three textures used in turn, with a fence for the frame drawn before, so the wait is normally none. If a fence wait times out or fails, `ring` finishes OpenGL's work before it reuses the texture. `ring` also waits (at most 20 ms) for the Direct3D conversion of the frame to finish before OpenGL takes the texture, because only NVIDIA is known to do that when the texture is locked. On one Intel laptop display `ring` still tore, so it is not the fix there; it stays the default for non-NVIDIA cards because it costs no stall. To compare the modes on one machine and clip, record dropped frames, visible artifacts and seeking. The app log says which one is used ("d3d11-dxinterop: waiting for OpenGL by ..."). To compare on one machine, set the environment variable `CJ_VSR_SYNC` to `finish`, `ring` or `none` before starting the app.

**Intel VSR compatibility mode.** On the Intel laptop display where `ring` still tore, a build that copies each upscaled frame back to system memory fixed the tearing on the same scene, with Intel VSR still running (804p to 1448p). That result shows that avoiding the shared texture fixes the symptom on that machine; it does not show which part of the driver fails inside the shared-texture path. `0002-intel-vsr-copyback.patch` does the copy in `d3d11vpp`, after the Intel video processor pass: the frame is downloaded in its own format (NV12 or P010) with all its attributes, the hardware frame is released, and a failed transfer takes the filter's usual failure path. It only applies when the scaling mode is Intel VSR, the hardware device belongs to `d3d11-dxinterop`, and it is asked for: by the filter option `intel-copyback=yes` (the app's "Intel VSR compatibility mode" switch in Settings, on by default) or by `CJ_INTEL_VSR_COPYBACK=1` for testing. The log says "d3d11-dxinterop: Intel VSR output uses copy-back". It is on by default in the app because the faster shared-texture path tore on the test display; copying is slow, though: 1080p60 upscaled to 4K60 stuttered badly with it, while 804p playback was normal, so the switch can be turned off. NVIDIA and native Direct3D 11 playback stay on their existing paths.
